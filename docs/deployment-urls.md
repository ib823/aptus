# Deployment, hostnames and URLs

What is deployed where, which hostname is canonical, and which settings depend
on that choice. Written 2026-07-25 against the live Vercel project.

---

## 1. There is one deployment, not two

`aptus-sandy.vercel.app` and `ab-workbench.vercel.app` are **the same thing**.

One Vercel project (`aptus`) serves four hostnames. They resolve to the same
deployment, the same build, the same environment variables and the same
database:

| Hostname | What it is |
|---|---|
| `ab-workbench.vercel.app` | **Canonical.** The one to publish and use. |
| `aptus-sandy.vercel.app` | Vercel's auto-generated production alias. Not removable, not a backup. |
| `aptus-ikmals-projects-4ec38ef0.vercel.app` | Account-scoped alias. |
| `aptus-git-main-ikmals-projects-4ec38ef0.vercel.app` | Branch alias for `main`. |

There is no second solution and no second database. Deploying once updates all
four; breaking the deployment breaks all four.

### Why they nonetheless feel like separate products

`*.vercel.app` is on the [Public Suffix List](https://publicsuffix.org/), so a
cookie set on one `*.vercel.app` hostname **cannot** be read on another. Each
hostname therefore has its own independent login session. Signing in on
`aptus-sandy` does not sign you in on `ab-workbench`.

This is a browser rule, not a bug and not something the app can override. It is
the single strongest reason to use exactly one hostname.

---

## 2. `aptus-sandy` is not a backup

It cannot be. It is the same deployment behind a different name — if the build
is broken, both are broken; if the database is down, both are down.

A real standby would be a **separate Vercel project with its own database**, kept
in sync deliberately. That is a different piece of work, and worth doing only if
the POC needs a recovery target. Database backups are the more useful thing to
have first, and they come from the Postgres provider, not from Vercel.

## 3. The canonical host is already configured

All three URL settings already point at `ab-workbench.vercel.app`:

| Variable | Set to | Used for |
|---|---|---|
| `NEXTAUTH_URL` | `https://ab-workbench.vercel.app` | Magic links, invitations, login-notify emails, WebAuthn origin |
| `NEXT_PUBLIC_APP_URL` | `https://ab-workbench.vercel.app` | Page metadata, sitemap, presales public origin, Affirm grant links |
| `WORKBENCH_HOST` | `ab-workbench.vercel.app` | Host-routing and the magic-link host rewrite |

So links generated by the app always point at `ab-workbench`, whichever hostname
the browser happened to be on. Someone who signs in from `aptus-sandy` and
requests a magic link is silently moved to `ab-workbench` — harmless, but a good
reason not to circulate the other names.

### Where URLs are built

- `src/lib/auth/send-magic-link.ts` — magic links; fails closed if `NEXTAUTH_URL` is unset
- `src/lib/auth/auth-options.ts` — the NextAuth sign-in path, with the same host rewrite
- `src/app/api/organizations/[orgId]/users/route.ts` — invitation links
- `src/lib/auth/login-notify.ts`, `src/lib/email/templates.ts` — security emails
- `src/lib/auth/webauthn.ts` — **passkey Relying Party ID**, derived from `NEXTAUTH_URL`'s hostname
- `src/lib/http/app-origin.ts`, `src/lib/presales/public-origin.ts` — server-side origin resolution

`COREEDGE_BASE_URL` is different: it is set by the **developer**, in the
scaffolded client, and points at `https://<canonical-host>/api/northbound`. It is
not a server variable and is deliberately unset in production.

## 4. Single-host mode, and how it gates routes

`WORKBENCH_ONLY=true` means this deployment presents **only** the Workbench.
`src/middleware.ts` redirects every page route outside `WORKBENCH_PATHS` to
`/workbench`.

That allow-list lives in `src/lib/routing/workbench-paths.ts`. It is a routing
**gate**, not decoration: anything absent from it is redirected away before the
route runs — before auth, before RBAC. A surface can be complete, tested and
deployed and still sit behind a locked door.

This has bitten twice. CoreEdge Console shipped across nineteen PRs while
`/studio` was missing from the list; Operations Center and Control Tower then
did the same thing. Both were invisible to the E2E suite, which runs against
`localhost:3003` where `WORKBENCH_ONLY` is unset. `/studio`, `/operations` and
`/control-tower` are all in the list now, and a test asserts they stay there so
the next surface fails CI rather than failing silently in production.

**Adding a surface to the Workbench means adding it to `WORKBENCH_PATHS`.**

---

## 4a. Both hostnames currently behave identically

Measured 2026-07-25, every route resolves the same on both, differing only in
hostname:

| Path | Result on either host |
|---|---|
| `/` | → `/workbench` |
| `/workbench`, `/presales`, `/sap-explorer` | → `/presales/login` (auth) |
| `/assessments`, `/dashboard` | → `/workbench` |

After signing in, **both hostnames land on `/workbench`**. The Aptus portal is
not reachable on either. They are not two products today.

### The two-product split exists but is switched off

`src/middleware.ts` implements a host-based split, gated on `WORKBENCH_HOST` **and**
`PORTAL_HOST` both being set. `PORTAL_HOST` is unset, and `WORKBENCH_ONLY=true`
short-circuits before that block runs. Enabling it would give:

| | `WORKBENCH_HOST` | `PORTAL_HOST` |
|---|---|---|
| Product | ABeam Workbench | Aptus portal |
| Serves | `/workbench`, `/presales`, `/sap-explorer`, `/affirm`, `/c/` | `/dashboard`, `/assessments` |
| Everything else | → `/presales` | Workbench paths → Workbench host |

**Before enabling it, note two things.**

1. `NEXTAUTH_URL` must become the **portal** host. `send-magic-link.ts` rewrites
   to `WORKBENCH_HOST` only for `/presales`, `/affirm` and `/c` callbacks and
   uses `NEXTAUTH_URL` for everything else — so with `NEXTAUTH_URL` left on the
   Workbench host, a portal user's magic link sets its cookie on the wrong origin
   and lands them on `/presales` instead of `/assessments`.
2. Moving `NEXTAUTH_URL` changes the derived WebAuthn RP ID, which invalidates
   every passkey already registered (see §5).

Recommendation for the POC: **stay single-host**. The separation is easy to hold
mentally, and splitting costs a passkey reset plus a second login surface to keep
working.

## 5. Recommendations

**Keep one published hostname.** `ab-workbench.vercel.app` is already canonical
in config; the rest is discipline — never paste the others into a ticket, email
or bookmark. You cannot delete Vercel's generated alias, and you do not need to.

**A custom domain is a future item, owned by ABeam HQ — not actionable here.**
Recorded so the cost is known when it happens, because two things bind to the
hostname and break when it changes:

1. **Passkeys.** The WebAuthn Relying Party ID is the hostname. Credentials
   registered on `ab-workbench.vercel.app` **will not work** on any other domain,
   and cannot be migrated — every user re-registers.
2. **Links already sent.** Magic links, invitations and Affirm guest links carry
   an absolute URL. Anything already in someone's inbox keeps pointing at the old
   host.

The cheapest moment to move is while the users are a handful of internal testers;
the cost rises with every passkey registered and every link emailed. When ABeam
HQ does provision a domain, `NEXTAUTH_URL`, `NEXT_PUBLIC_APP_URL` and
`WORKBENCH_HOST` must be changed **together** — they must agree — and
`WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGIN` should be set explicitly rather than left to
derive, so any later hostname change is a deliberate act rather than a silent
one.

A custom domain would also remove the Public Suffix List problem: on
`abeam.com`, cookies *can* be shared across subdomains if that is ever wanted.

Until then, `ab-workbench.vercel.app` is the fixed URL. Treat it as the one that
goes in emails, bookmarks and client-facing material.

**Do not treat any alias as a backup.** If the POC needs a recovery story, that
means database backups first, and a separate standby project only if downtime is
genuinely unacceptable.

## 6. Access for testing

This deployment's internal-testing posture — which bypass surfaces are enabled,
under which environment flags, and what is left protecting them — is deliberately
**not documented in this repository**, which is public. It is held with the
deployment's environment configuration.

What belongs here is the rule, not the current state: the test-login path is
gated by `src/lib/auth/dev-login.ts` and `scripts/check-production-env.js`
refuses to build a deployment that enables it without
`INTERNAL_TEST_DEPLOYMENT=true`. **None of it belongs on a customer-facing
deployment.**

RBAC note that is safe to state: `canMutateStudio` is consultant-only by design,
so `platform_admin` gets read-oriented oversight and finds the
create/register/decide actions disabled.
