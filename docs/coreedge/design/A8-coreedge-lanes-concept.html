CoreEdge · redesign concept · 11 Sep 2026

CoreEdge Lanes

A rethink of CoreEdge around the work people actually do, rather than the tables it stores. It is built for ABeam consultants first: those who build client apps, those who approve their access, and the operators who keep them running.

For: CoreEdge product team Grounded in the 10–11 Sep end-to-end run Status: concept for decision
The idea

Stop asking people to line up six objects across three screens. Give every app one lane per environment, where access, SAP system and key either match by construction or say exactly what is missing.

The governance engine stays as it is: grants checked on every call, environment binding, honest status, audit. What changes is how people see it and act on it.

Navigation mirrors the database

Six tabs, one per stored object. A builder's one job is spread across all six, in an order nobody explains.

One console for four jobs

Builder, reviewer, operator and admin share screens. Roles hide buttons rather than giving each person a view of their own work.

The rule that matters is invisible

Access environment = key environment = SAP system environment. You only learn it by failing, which is how a key landed on the empty twin solution.

Fourteen nouns before a first call

Solution, interface, capability, catalogue service, entity set, grant, credential, client, connection, tenant, environment, binding, broker, northbound.

Signals that contradict

"Reachable" while reads return 403. "Activated" on one screen, "Needs setup" on another. "PASS · unevidenced".

Handoffs happen off-screen

Nothing tells the approver a request is waiting, or the builder that a key is ready. People coordinate in chat.

The shift

Six rules the new design has to obey

1

Organise around the job, not the table

The screen is "my app's purchase orders in Test", not "the grants ledger". Objects show up only inside the job that needs them.

2

Make the mismatch impossible, not explained

If access, key and SAP system always belong to one lane, they can't disagree. A whole class of error disappears.

3

Every person starts from "what needs me"

One queue per person across roles: review this, collect that key, fix this failing read. Nobody goes looking for work.

4

Proof, with its age

A status is a check that ran: what it tested, when, and what it doesn't prove. Old proof fades to "unknown" by itself.

5

Every refusal is a route to its fix

A failed call traces itself hop by hop, names the broken hop and its owner, and offers the one action that fixes it.

6

Plain words up front, SAP terms one click away

"Purchase orders" and "Test", with CE_PURCHASEORDER_0001 / PurchaseOrder in a details drawer for the consultant who wants it.

The new model

An app has data feeds; each feed has a lane per environment

A lane is the unit people reason about. It holds four gates, always in the same order, so everyone reads the same state the same way. The environment belongs to the lane, not to each object separately, so the three-way match can't be broken.

The golden path

From idea to Test data, and a failure that handles itself

A builder's first data feed

  1. 0:00
    Builder

    Creates "Purchase Order Tracker". Types "purchase orders" in the catalogue and adds the feed; the fields come from $metadata.

    Today: Discover → Add to interface → Interfaces → set entity set by hand.
  2. 0:03
    CoreEdge

    Opens a Sandbox lane at once, with a key the builder collects via coreedge pull. The typed client works against sandbox data.

    Today: no path to any data without an approved grant.
  3. 0:40
    Builder

    Clicks Promote to Test. The review opens pre-filled: fields, system X5M/100, expiry 90 days, checks already running.

    Today: raise a grant, remembering to pick an expiry and the right environment.
  4. 0:52
    Reviewer

    Sees it at the top of Needs you. All checks green, so approves with one click. SoD is enforced, and shown in plain words.

    Today: someone has to tell them in chat; then sign-out, sign-in as another account.
  5. 0:53
    CoreEdge

    Issues the Test key to the owner. The builder's queue says "Key ready"; coreedge pull --env test updates .env.

    Today: a different person issues the key, sees the token, pastes it somewhere.
  6. 0:55
    Builder

    First Test call returns 5 rows. The lane's T gate turns green; the timeline logs "first call".

A failure, operator to builder

  1. 09:10
    CoreEdge

    The scheduled check on Bank details · Dev reads metadata 200 but data 403. The S gate turns red and the lane fades out of "Live".

    Today: "Reachable" stays green; Discover says "Activated".
  2. 09:10
    Operator

    Sees it on the board with the owner and client. Opens Why: the broken hop is "SAP data read", owned by the client's SAP admin.

  3. 09:12
    Operator

    Clicks Send to SAP admin. CoreEdge drafts the note: communication user, service, entity set, the 403 and what to check.

    Today: someone reads the code to work out a 401 from a 403.
  4. 09:12
    Builder

    Their queue shows "Bank details · Dev blocked by SAP, operator on it". There's nothing to debug, and the timeline shows who is doing what.

  5. 14:30
    CoreEdge

    The next check passes. The lane goes live and both people get "Resolved · SAP authorisation fixed", linked to the timeline entry.

What stays underneath

The engine is good. The lane is a new way to read it.

Nothing in CoreEdge's governance has to be thrown away. Grants still gate every call, the environment binding still refuses cross-landscape reads, secrets stay sealed, and every call is audited. A lane starts as a read model that joins what already exists:

Lane(app, feed, environment) = Solution → app Interface → feed (+ dataset, fields) ApiAccessGrant → A gate SapConnection → S gate (+ probes, age) SolutionClient → K gate (per env since AD-11) NorthboundAudit → T gate + timeline

New pieces, in build order

Lane endpoint. GET /apps/:id/lanes composes the joins above with the broker's own predicates, so the board can never disagree with a real call.

Per-lane checks. A scheduled metadata probe plus a 1-row data read per lane, stored with timestamps (review item TECH-05).

Promote action. Opens the access request pre-filled for the next environment with an expiry, then issues the key to the owner when it's approved.

Timeline and queue. An event stream built from audit, grant, key and probe records, plus a per-person "needs you" query over it.

Plan

Three phases, each shippable on its own

Phase 1 · ~4 weeks

See it

  • Lane endpoint and the app lane board
  • Needs you queue (read-only)
  • Why? trace on every refusal
  • New words across the UI
Exit: a consultant new to CoreEdge gets a first Test read in under 30 minutes without help.
Phase 2 · ~6 weeks

Flow it

  • Promote and review with checks
  • Scheduled per-lane checks with age
  • Keys delivered to the owner (claim link, then CLI)
  • Shared timeline; one Operations workspace
Exit: zero account-switching to hand work over; reviews answered within 4 hours.
Phase 3 · next quarter

Scale it

  • Instant sandbox lanes (AD-12)
  • Field-level contracts and typed SDK from $metadata
  • ABeam lane blueprints
  • Explore: MCP access, client passport, Ask CoreEdge
Exit: a second client landscape onboarded from a blueprint in a day.
Before Phase 1 ships to anyone outside the team: close the three open P0s from the fix verification: the dev-login backdoor live in production, the ungoverned Studio explorer read path, and caller-chosen entity sets. A friendlier front door on an open back door makes the risk worse.

Your call

Six decisions that shape the build

  1. Adopt the lane as CoreEdge's core object and rename the product vocabulary?Everything else follows from this. The database keeps its names; the UI and docs change.
  2. Merge Operations Center and Control Tower into one Operations workspace?Operators and admins currently split across 13 screens; the board plus drill-downs covers both.
  3. Key delivery: claim link first, or CLI first?The claim link is quicker to build; the CLI is what builders will actually use daily. Both remove "the issuer sees the token".
  4. Instant sandbox: who holds the SAP API Hub key?One ABeam-owned key per CoreEdge deployment is simplest; per-consultant keys are cleaner for audit.
  5. Keep SAP terms visible for consultants, or behind a details drawer?Consultants read CE_PURCHASEORDER_0001 fluently; client users and new joiners don't. A per-person "show SAP names" toggle serves both.
  6. Put the client integration passport into the next pitch?It turns governance into something a client CIO can see, and no one else in this market shows it.
