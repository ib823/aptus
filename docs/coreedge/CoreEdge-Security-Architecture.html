Trust boundaries, controls, and an honest gap register

How CoreEdge protects client SAP systems and data as a multi-tenant middleware. Written for an InfoSec review: every control is marked built, built, lenient by default (shipped, but a deployment setting decides whether it refuses), or not built with the roadmap item that adds it. Each built control points to real code or a test. The gaps are named, not hidden.

Reviewer's summary. The northbound broker, per-tenant SAP credential sealing, tenant scoping and the per-call audit are built and in production: a solution calls SAP through CoreEdge with its own hashed key, only for an interface a second person approved, in one environment, until the approval expires, and every call (refusals included) leaves an audit row. Several of the newer controls ship lenient by default so that deploying them locks nobody out: passkey step-up warns rather than refuses, legacy grants keep their old matching, and the tenant guard logs rather than throws in production. Each has a setting and a runbook for switching it on. What is not built: a consumer OAuth token endpoint, a cloud KMS, fail-closed and tamper-evident audit writes, staff SSO, quotas and budgets beyond fixed rate limits, and private-network reach. Section 4 lists each with its roadmap item (docs/coreedge/CoreEdge-Gap-Study-and-Roadmap.md).

1Posture at a glance

✔ Built & tested today

  • Northbound broker: reads and creates through /api/northbound/*, one static key per solution and environment, hashed (SHA-256) and shown once (lib/northbound/auth.ts, read.ts, write.ts)
  • Grants: two-person approval, mandatory expiry checked on every call, bound to one interface and SAP product (lib/studio/grants.ts, grant-binding.ts)
  • SAP secrets: AES-256-GCM, bound to their row, under per-organisation data keys with versioned master keys (connection-crypto.ts, secret-envelope.ts)
  • Key hygiene: TEST and PROD keys expire, rotation overlaps, ce_live_/ce_test_ prefixes, published scanning patterns (lib/northbound/key-policy.ts)
  • Per-call audit: one row per call, refusals included, with a correlation id (NorthboundAuditEvent, lib/northbound/audit.ts)
  • Write safety: write grant, separate write key, per-connection writeEnabled, mandatory Idempotency-Key (lib/northbound/idempotency.ts)
  • Abuse/DoS: rate limits per credential on machine routes, per IP elsewhere; a limiter outage refuses with 503 (security/rate-limit.ts, middleware.ts)
  • Staff identity: magic-link sign-in plus WebAuthn passkeys (api/auth/webauthn/*)
  • Assurance: authn / authz / data-protection / injection suites, a governance property test, security-headers test

◐ Built, lenient by default

  • Passkey step-up on governance actions — COREEDGE_STEP_UP defaults to warn: the action proceeds and a STEP_UP_MISSING audit row records it set enforce
  • Grant binding — COREEDGE_GRANT_BINDING defaults to legacy: a grant approved before binding keeps its old matching on the interfaces that existed at the deploy set strict
  • Tenant-scope guard — TENANT_SCOPE_GUARD defaults to log in production (throw elsewhere); each violation is counted in TenantGuardViolation set throw
  • Envelope encryption — off until SAP_CONNECTION_ENCRYPTION_ACTIVE_KEY is set; the only key provider is the environment set active key

○ Not built

  • Consumer OAuth 2.0 token endpoint and short-lived tokens P2.5
  • A cloud KMS key provider P0.10 follow-up, open decision
  • Fail-closed, hash-chained audit writes and export P3.10
  • Staff SSO (OIDC/SAML) and SCIM P4.6
  • Quotas, budgets and policy packs P3.5

6Data protection & tenancy

What CoreEdge stores

  • Connection metadata — tenant key, product, non-secret baseUrl, SAP client, auth type, health
  • Sealed secrets — AES-256-GCM ciphertext only, under a per-organisation data key; the master key is never stored in the database
  • Catalogue + stored probe status — tenant-keyed; design-time, not business data
  • Audit metadata — who/what/when/outcome per call and per configuration change; not raw payloads
  • Short-lived cached reads — Workbench live reads cached in-process for 30 s, keyed by whose system answered; northbound responses are no-store

Principles

  • Business data is read-through, not warehoused — CoreEdge brokers, it does not become a second copy of client data
  • Responses normalized + redacted; sensitive fields masked by default
  • Every store is tenant-scoped; isolation is structural, not conventional
  • Diagnostic payloads (if ever retained) are tightly scoped, redacted, and access-logged
  • Audit retention is configurable (NORTHBOUND_AUDIT_RETENTION_DAYS, 7-3,650 days); a dedicated deployment is the option for residency constraints
Deliberate design choice: the audit/log store must not quietly become a second uncontrolled repository of client data. Audit metadata, operational metrics, and (rare, redacted) diagnostic payloads are separated — so logging strengthens governance instead of widening the blast radius.

8Roadmap to "defensible"

The four builds this page first listed (land the credential keystone, build the northbound broker, enforce tenant isolation, add a per-call audit) have shipped. What remains, in the order the roadmap takes it:

1 · Switch the lenient defaults on — COREEDGE_STEP_UP=enforce, COREEDGE_GRANT_BINDING=strict, TENANT_SCOPE_GUARD=throw, an active envelope key. Operator steps, each with a runbook and a check that says when it is safe. settings

2 · A cloud KMS key provider — so the master key never sits in the deployment environment. Needs the product owner's choice of KMS. open decision

3 · Consumer OAuth 2.0 — client credentials with short-lived, sender-constrained tokens beside the static keys. P2.5

4 · Audit integrity v2 — fail-closed writes, a hash chain with daily anchors, and export. Closes the rest of B7. P3.10

Bottom line for InfoSec: the platform controls an InfoSec review asks about are built and in production; several ship lenient so that deploying them locked nobody out, and switching them to refuse is a setting, not a build. The gaps that remain are named above with the roadmap item that closes each.
