CoreEdge · Security Architecture

Trust boundaries, controls, and an honest gap register

How CoreEdge protects client SAP systems and data as a multi-tenant middleware. Written for an InfoSec review: every control is marked built, keystone (built, pending merge), or planned, and each built control points to real code or a test. No overstatement — the gaps are named, not hidden.

Reviewer's summary. The security primitives are mature and tested — phishing-resistant staff auth (passkeys + MFA), AES-256-GCM secret sealing, rate-limiting, input sanitization, redaction, session-token hashing, security headers, and dedicated authn/authz/data-protection/injection test suites. The CoreEdge-specific spine — the northbound API broker, tenant-isolation enforcement, and the per-call audit store — is designed but not yet built. This document states exactly which is which.

1Posture at a glance

✔ Built & tested today

  • Staff identity: NextAuth + WebAuthn passkeys + MFA; per-host session isolation (api/auth/webauthn/*, middleware.ts)
  • Authorization: RBAC guards + admin role tests (lib/auth/admin-guard.ts, tests/security/authorization.test.ts)
  • Crypto: AES-256-GCM sealing (ai-key-crypto.ts; keystone secretsCiphertext)
  • Abuse/DoS: rate-limit + tight live-SAP bucket (security/rate-limit.ts · isLiveSapTenantRoute)
  • Input/replay: sanitize, HMAC-nonce, safe filenames, session-token hashing (security/*)
  • Data: redaction + no-host-leak (presales/redaction.ts + external-redaction e2e)
  • Supply chain: Dependabot + resilient audit gate (#124)
  • Assurance: authn / authz / data-protection / injection test suites + security-headers test

◔ The spine still to build

  • Land the keystone — per-tenant SAP secret sealing into production keystone
  • Northbound broker — OAuth2 client-credentials, per-solution identity, tenant-bound scopes, quotas planned
  • Tenant-isolation enforcement + tests — prove A can't read B even by tampering planned
  • Per-call audit store — who/what/when/outcome (also the monitoring source) planned
  • Write idempotency + duplicate prevention planned
  • Portal governance — approval gates, progressive trust, config-change audit planned

6Data protection & tenancy

What CoreEdge stores

  • Connection metadata — tenant key, product, non-secret baseUrl, auth type, health
  • Sealed secrets — AES-256-GCM ciphertext only; keys never at rest in plaintext
  • Catalogue + stored probe status — tenant-keyed; design-time, not business data
  • Audit metadata — who/what/when/outcome (planned); not raw payloads
  • Short-lived cached reads — 30s TTL, tenant-scoped, not durable

Principles

  • Business data is read-through, not warehoused — CoreEdge brokers, it does not become a second copy of client data
  • Responses normalized + redacted; sensitive fields masked by default
  • Every store is tenant-scoped; isolation is structural, not conventional
  • Diagnostic payloads (if ever retained) are tightly scoped, redacted, and access-logged
  • Retention & residency configurable per tenant (dedicated-deployment option for stricter needs)
Deliberate design choice: the audit/log store must not quietly become a second uncontrolled repository of client data. Audit metadata, operational metrics, and (rare, redacted) diagnostic payloads are separated — so logging strengthens governance instead of widening the blast radius.

8Roadmap to "defensible"

Four builds turn a strong posture into one that passes a client's security review. In dependency order:

1 · Land the keystone — per-tenant SAP secret sealing in production. Closes the crown-jewel boundary (B3). built, merge it

2 · Northbound broker — OAuth2 client-credentials, per-solution identity, tenant-bound scopes, quotas. Closes B2 and enforces least privilege for solutions. planned

3 · Tenant-isolation enforcement + test suite — tenant-from-token everywhere; prove A can't reach B under tampering. Closes B4. planned

4 · Per-call audit store — immutable who/what/when/outcome with correlation IDs. Closes B7 and feeds the monitoring dashboard. planned

Bottom line for InfoSec: CoreEdge is built on mature, tested security primitives, with a clearly-scoped set of platform controls remaining. Nothing here is hand-waved — every claim is code-backed or explicitly marked as planned. The four builds above are the path to a defensible, review-ready platform.
